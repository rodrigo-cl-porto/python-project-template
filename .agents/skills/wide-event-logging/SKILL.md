# Wide Event Logging

Logging conventions of this repository, from **[Logging Sucks](https://loggingsucks.com/)**, which proposes **wide
events**, also called **canonical log lines**. Instead of logging what the code is doing, log *what happened to this
unit of work*. These conventions complement [`AGENTS.md`](../../../AGENTS.md),
[`code-standards.md`](../../rules/code-standards.md) and
[`architecture-standards`](../architecture-standards/SKILL.md).

## When to use this skill

- **Events generated by the application:** a request, CLI command, scheduled job, use case or any business operation
  whose outcome must be recorded.
- **External events the application receives:** webhooks, queue or stream messages, scheduled triggers, files dropped
  in a watched folder, signals from other systems.
- **External events the application may run into:** calls to external APIs, databases, file systems, email or any
  other service that can be slow, time out, refuse the request or answer with an error.

## Workflow

1. Add structlog if it is missing: `uv add structlog`.
2. Create (or reuse) `adapters/code_origin.py` and `adapters/observability.py` following
   [`references/example.md`](references/example.md). Keep each file under 100 lines.
3. Call `configure_logging()` once in the composition root (`bootstrap.py`), so the events go to
   `logs/events.jsonl` at the repository root.
4. Decorate each inbound adapter (unit of work) with `@wide_event("<operation>", channel="<channel>")`.
5. Enrich the current event from use cases and adapters with `structlog.contextvars.bind_contextvars(...)`.
6. Check that `logs/` is listed in `.gitignore` (it already is in this template); add it back if it was removed.
7. Test the event content and the `.jsonl` output (see [Testing](#testing)).

## 1. Use structlog, never `logging` or `print`

**Do not use the standard `logging` module directly**, nor `print` for diagnostics. Use
**[structlog](https://www.structlog.org/)**, configured to render JSON.

## 2. Always persist the events to `.jsonl` files in `logs/`

**Every wide event is always persisted to a [JSON Lines](https://jsonlines.org/) file (`.jsonl`) inside the `logs/`
folder at the root of the repository** (`logs/events.jsonl`): one complete JSON object per line, UTF-8 encoded,
appended at the end of the file. Never write events to the console only, to another folder or in another format.

- Configure structlog with `structlog.processors.JSONRenderer()` as the last processor and
  `structlog.WriteLoggerFactory` writing to the `.jsonl` file opened in append mode (`"a"`).
- Never pretty-print (`indent`) the events: a multi-line JSON object breaks the JSON Lines format.
- Resolve the `logs/` folder from the location of the code (`Path(__file__)`), never from the current working
  directory, so it is always the folder at the repository root. Create it if it does not exist.
- `logs/` holds runtime data and **must always be listed in `.gitignore`**: event files are never committed.

## 3. Emit one wide event per unit of work

- **Emit one wide event per request (or per unit of work: CLI command, job, message) per service.** Build the event
  throughout the request lifecycle and emit it **once, at the end**, instead of scattering many small log lines.
- **Structured, not strings:** every piece of information is a key-value field, never interpolated into a message.
  `{"event": "payment_failed", "user_id": "123"}`, not `"Payment failed for user 123"`.
- **High cardinality and high dimensionality:** include identifiers (`request_id`, `trace_id`, `user.id`,
  `order.id`) and as much business context as is useful (subscription tier, cart value, feature flags, attempt
  number, etc.). More fields mean more questions you can answer later.
- Use consistent field names across the codebase (always `user_id`, never `userId`, `user` and `uid` in different
  places) and nest related fields (`user.*`, `cart.*`, `payment.*`).

## 4. Handle external events

- **Received external events** (webhook, message, trigger, file) are units of work: the inbound adapter that receives
  each one is decorated with `@wide_event`, so every received event produces its own wide event. Include the
  `channel` (`webhook`, `queue`, `scheduler`, ...), the `source` system and the external identifiers
  (`message_id`, `delivery_id`, `file.name`), never the raw payload.
- **Interactions with external services** do not create new events: they enrich the current one with a nested field
  named after the dependency, e.g. `payment = {"provider": "stripe", "attempt": 2, "latency_ms": 1089,
  "status_code": 200}`.
- **Failures of external services** (timeouts, refused connections, error responses) end up in the `error` field of
  the current event, with `retriable` telling whether a retry could succeed. `origin` points to the project code that
  called the external service.

## 5. Always include the mandatory fields

Every wide event must contain:

| Field                         | Content                                                                                  |
| ----------------------------- | ---------------------------------------------------------------------------------------- |
| `timestamp`                   | **Date and time of the execution**: when the unit of work started, in ISO 8601 and UTC.  |
| `origin.file`                 | **Name of the file where the main event occurred**, relative to `src/`.                  |
| `origin.function`             | **Name of the method or function where the main event occurred** (`Class.method`).       |
| `service`, `version`          | Service name and its SemVer version (read with `importlib.metadata.version`).            |
| `deployment_id`/`environment` | Where the service is running.                                                            |
| `request_id`                  | Unique identifier of the unit of work.                                                   |
| `duration_ms`                 | How long the unit of work took.                                                          |
| `outcome`                     | `success` or `error`.                                                                    |
| `error`                       | Only on failure: an object with `type`, `message`, `code` and `retriable`.               |

For example: `"timestamp": "2026-01-15T10:23:44.365+00:00"` and
`"origin": {"file": "my_awesome_project/application/use_cases.py", "function": "Checkout.execute"}`.

The **main event** is what defines the outcome of the unit of work:

- **On success**, it is the unit of work itself, so `origin` points to the function or method decorated with
  `@wide_event` (usually the inbound adapter).
- **On failure**, it is the error, so `origin` points to the deepest function or method **of the project** in the
  traceback, which is where the exception was raised. When the exception comes from a third-party library, `origin`
  points to the project code that called it.

Capture `origin` from code objects (`__code__` and traceback frames), never by hardcoding strings: hardcoded names
become wrong as soon as the code is renamed or moved.

## 6. Apply tail sampling

Decide whether to keep the event **after** it is complete. Always keep errors, slow requests and important users;
randomly sample the remaining happy-path events.

## 7. Never log sensitive data

Never log secrets or sensitive data (passwords, tokens, full card numbers, personal documents), nor raw payloads of
external events that may contain them. See also
[Never put sensitive data in the code](../../rules/code-standards.md#13-never-put-sensitive-data-in-the-code).

## 8. Respect the architecture

The domain layer stays pure and does not log. Wide events are started by inbound adapters, enriched by use cases and
adapters, and configured in `adapters/observability.py` (see
[Ports and Adapters](../architecture-standards/SKILL.md#ports-and-adapters)).

## Testing

Follow [`tests.md`](../../rules/tests.md):

- **Unit tests** cover `should_keep`, `describe_code` and `find_raising_code`, and assert the fields bound by use
  cases with `structlog.testing.capture_logs()`.
- **Integration tests** pass a `.jsonl` file inside `tmp_path` to `configure_logging`, so they never write to the real
  `logs/` folder, run a decorated unit of work and assert that each line is a valid JSON object with the mandatory
  fields.
- Make tail sampling repeatable in tests by forcing `outcome="error"` or by patching the random sampling.
